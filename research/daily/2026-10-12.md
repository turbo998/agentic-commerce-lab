### UCP handler：从“发现能力”到“执行能力”不能跳步

官方 handler 正文明确：card 通过 `/api/ucp/tokenize` 得到 SPT；Apple Pay 直接提交 wallet token，不走 card tokenize；Google Pay 使用 `com.google.pay` handler。虽然 discovery 可宣告 `link`，**当前 `/complete` 不接受 `link` instrument**。Link Agent Wallet 获取 SPT 与 UCP completion 接受何种 instrument 是两个问题。

Tokenize 还要求 agent/seller 相同环境且有已确认的 commerce relationship；`identity.access_token` 在这里是卖家的 Stripe network profile ID，不是客户 OAuth access token。这与 Link 的 customer OAuth、MCP 的 OAuth/Agent Key 都不应混同。

方案选型必须校验 `(protocol version, handler version, instrument, environment, relationship, geography)`；能力宣告不是成功证据。采集原始 card credential 引入 PCI 责任，不应进入 LLM 上下文。本轮没有执行 tokenize、采集卡信息或声称通过 conformance。

### Stripe MCP：19 个日历日的迁移窗口

2026-10-12 到 2026-10-31 相差 **19 个日历日**，不是精确剩余小时。官方正文没有说明 cutoff 的时区/具体时刻，因此不要假设北京时间午夜切换，也不要等到最后一天。

官方说明期限开始后 full-access secret keys 和无 Agent tag 的 restricted keys 会得到 `401` + OAuth discovery challenge。交互客户端优先 OAuth；不能 OAuth 的 autonomous client 使用新建最小权限 Agent Key，先 sandbox 验证，再 expire 旧 key。这是 Stripe MCP 的认证政策，不是宣称所有 Stripe API、UCP tokenize 或 Link API 都在同一天禁止同类 key。

**建议的迁移验收，不是本次已执行的账户操作：**按 account/environment/client 盘点类别 → 由账户负责人确认权限与 approval rules → sandbox 验证所需 read/write 及敏感操作审批 → 有人工授权后推广并撤销旧 key/session → 确认撤销范围。MCP OAuth 撤销按正在查看的 account/organisation 和环境生效，不应假设一次撤销覆盖所有账户。禁止因 401 回退到更高权限 key、自动创建账户或绕过审批。

本轮还阅读 Stripe 链接到的 [MCP `2026-07-28` authorization overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)：HTTP OAuth resource metadata/discovery/scope；不是完整新规格审阅，更不是支付授权标准认证。

## 4. 辩证架构：AI Native 不是放弃 Well-Architected

**先纠正比较对象。** Well-Architected 是质量属性、风险和取舍的评估框架；[N-tier](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier) 是架构风格，逻辑层不必对应独立物理 tier，还可以使用异步消息。不能将两者都简化成“Web → App → DB”。

今天直接核验的 [Azure WAF AI application design](https://learn.microsoft.com/en-us/azure/well-architected/ai/application-design) 已划分 Client / Intelligence / Inferencing / Knowledge / Tools 五层，区分 deterministic orchestration 与 agent collaboration，并讨论工具策略、持久状态和带身份/策略/版本的缓存。**“云 WAF 不懂 Agent，因此必须替换”并不成立。** 下表是本研究对 Agentic Commerce 的领域补强，不是厂商标准。

| 设计维度 | 保留的 WAF / 常规应用原则 | Agentic Commerce 必须显式补强的对象 |
|---|---|---|
| 系统边界 | 职责分层、最小权限、隔离 | 推理层只能提出 action；确定性 authority 层掌管最终 cart、用户/商户/金额/币种/到期/撤销；credential broker 不向模型释放秘密 |
| 授权模型 | IAM/OAuth/RBAC 与 tenant 隔离 | 调用 API 的身份权利不等于消费者这笔交易的同意；订单授权、钱包 scope、卡网络控制、审批规则各自验证 |
| 工作单元 | 请求、服务 SLO、异步任务 | 有预算和终止条件的 task/transaction；对话结束不代表订单完成，用户批准可能晚于模型会话 |
| 状态与记忆 | 持久化、事务、一致性 | conversation memory 是推理材料，不是 consent/order/payment 账本；授权与经济状态不能从“模型记得已批准”恢复 |
| 可靠性 | 重试、熔断、outbox、saga | 经济副作用不能盲重试：冻结参数/原 key，`unknown` 先查询对账；revoke 与消费竞争在最终执行点解决；退款请求不等于到账 |
| Grounding / 缓存 | 数据 lineage、权限过滤、TTL | 目录是可能过期的证据；commit 前回查最终税费/运费/库存/条款。语义相似缓存不能复用支付批准；只读缓存与经济命令日志分开 |
| 测试与发布 | 单测、契约、故障注入、渐进发布 | 推理用场景/evaluation，授权用确定性负向断言；LLM judge 不裁定金额是否可付。model/prompt/tool/schema 变更均需回归，不能只跑 Web API happy path |
| 单位经济 | 成本优化、配额、限流 | 分开管控推理 token、工具调用、支付消费与累计预算；按正确完成的授权订单核算成本，不把低 token 成本等同于高业务价值 |
| 可观测性 | trace、metric、audit | 关联 task/quote/approval/policy version/request key/provider reference 与实际结果；最小化证据记录，不上传 raw financial data、凭证或隐式推理全文 |
| 演进与兼容 | API version、隔离 adapter、淘汰计划 | 维护角色/地区/preview/protocol/handler/instrument/auth 的兼容矩阵；今天的 Link instrument 和 MCP cutoff 就是不能只看营销名称的例子 |
| Agent 拓扑 | 简单设计、明确 bounded context | 比价/探索可并行多 Agent；checkout/扣款/退款用确定性编排。多 Agent 投票不产生用户授权，更多 Agent 也不天然更可靠 |

**推荐逻辑划分：**以已有 [参考架构](../architecture.md) 为起点，区分推理与知识面、确定性授权与执行面、经济状态与证据面。它们是逻辑信任边界，不强制微服务或独立数据库。先用模块化单体与异步订单事件，只有在凭证隔离、合规边界、团队或独立扩缩容确有需求时再物理拆分。服务越多，分布式授权消费和外部支付恢复反而越复杂。

**需要重新设计的不是三层“层数”，而是允许谁改变哪一个状态。** 先批准最终报价，再申请 scoped credential，外部支付保持 pending/unknown 直到可信 provider 结果确认；履约和补偿继续独立追踪。本地数据库事务不能把已发生的外部资金副作用回滚。Prompt injection 防护/模型输出过滤有价值，但不能代替最终执行点的授权校验。

验收建议（**非生产测量结果**）：权限负向测试集零放行、重复请求不增加经济副作用、模型/工具失败仍保留 recoverable 状态；分别测量报价延迟、人工批准等待、付款确认及履约完成时间。有限离线测试通过不证明生产“零风险”，基础设施 availability SLO 也不等于授权正确交易完成率。

## 5. 场景：从产品映射到执行边界

| 场景 | 本日细化的方案 | 明确验收与不能做的事 |
|---|---|---|
| 消费者对话购买 | ACP/UCP/Suite 管 discovery/checkout；Link 或其他 broker 管独立 spend approval；TAP 只管请求信任 | 最终 cart 漂移重新批准；Link instrument 不支持时先选择实际可用 handler/路径，不冒充支持、偷偷降级到浏览器付款 |
| 商户目录运营 Agent | 先 dry-run diff，再由商户系统确认 upsert/replace/delete；跟踪异步 import 结果与源版本 | 旧 import 晚完成不能覆盖新商业真相；展示 catalog 不代表库存仍在。当前实验不实现该 feed adapter |
| B2B 开票/售后 Agent | Visa Toolkit pilot 或 Stripe 工具访问分开读、创建发票、退款；敏感动作走独立授权/approval rules | 发票创建不是付款；工单重复不新增经济操作，查询权限不能扩大为退款权限 |
| 开发 Agent 购买 API/数据 | MPP/x402 的 payment challenge 在模型外核验收款方、资源、币种/网络、价格/期限，再消耗累计预算 | 任意 402 不自动付费；on-chain settled / Stripe recording unknown 时只重放记账，禁止再次转账 |
| MCP 客户端迁移 | 按环境审阅客户端元数据，优先处理 full-access/无 tag key，区分 OAuth 与 autonomous client | auth class 记录正确不证明有效 key、审批、市场准入或真实 API 权限；本轮只做合成离线盘点 |

补货、旅行、财务洞察等其余场景沿用 [既有场景与验收](../use-cases.md)，不重复实现它们。

## 6. 今日增量资产：无密钥 MCP 迁移盘点

```powershell

```

未传 `--as-of` 时取当天北京时间日期；显式传入仅做 calendar-date simulation，不假设 Stripe 的精确切换时刻。

| 输出与退出码 | 含义 |
|---|---|
| `migration_required`；exit 1 | 期限前发现旧 auth class；不能用“尚未被拒绝”输出绿色成功 |

| `recorded_supported_unverified`；只有全部如此才 exit 0 | operator metadata 记录 OAuth/Agent Key；`account_verification=not_performed`，不是账户或付款权限验证 |
