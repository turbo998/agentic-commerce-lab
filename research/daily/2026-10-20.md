## 2. 2026-10-20 一手协议规范与代码库审计发现（Stage 54）

### 2.1 Universal Commerce Protocol (`Universal-Commerce-Protocol/ucp`)
1. **PR `#982`（`fix(docs): restore bundled schema type links for ucp-schema 2.0.0 (#887)`，`2026-10-20` 更新）**：
   - **问题根因**：自 `ucp-schema 2.0.0`（`ucp-schema#66`）起，`ucp-schema resolve --bundle` 在内联跨文件 Schema 时会剥离非根节点的 `$id` 与 `$schema` 元数据。旧版 `_restore_fragment_refs` 仅恢复顶层属性的 `#/$defs/...` 片段引用，导致超过 400 个规范字段在打包后退化为无类型的 `object` 或 `Array[object]`；同时 `_resolve_schema` 未对 `schema_path` 执行 `Path(schema_path).resolve()` 归一化，导致相对路径与绝对路径产生重复缓存键。
   - **架构启示**：AI-Native 协议网关在进行 Schema Bundling 与 MCP Tool Schema 编译时，必须并行保留未打包源 Schema 的 `$ref` 拓扑图（覆盖属性、数组 `items`、`items.allOf` 分支及同文件 `#/$defs/...` 跨文件转发别名），并对路径缓存键执行绝对路径归一化。
2. **PR `#962`（`feat(catalog): add optional seller logo`）**：
   - **规范语义**：在共享目录变体 `shopping/types/variant.json` 的 `seller` 对象下新增可选 `logo` 字段（引用 `common/types/media.json`，建议使用 `type: "image"`、必填 `https://` `url` 与无障碍 `alt_text`）。
   - **安全与权限边界**：规范明确声明 `seller.logo` 仅作为变体展示的卖家视觉标识（区别于商品制造商），**不构成该卖家名称与 `/.well-known/ucp` 商业发现档案之间的密码学或身份绑定**；平台必须容忍缺省 `seller` 或缺省 `seller.logo`（仅展示 `seller.name`），严禁将展示层 `seller.logo` 当作商户结算或授权验签的信任锚点。

### 2.2 Agentic Commerce Protocol (`agentic-commerce-protocol/agentic-commerce-protocol`)
1. **PR `#310`（`Detect JSON Schema and OpenAPI property drift`）与 PR `#290` / `#284` / `#275`**：
   - **双源契约漂移检测（`#310`）**：ACP 同时发布 JSON Schema（`$defs`）与 OpenAPI 3.1（`components.schemas`），客户端生成工具任选其一。由于 OpenAPI 侧开启了 `additionalProperties: false`，任一单侧多出的字段都会导致跨语言 SDK 在运行时出现确定性互操作拒绝。PR `#310` 新增双向属性集合对比器并盘点出 **23 处既有漂移**（如 `CheckoutSessionBase/order`、`Address/company`、`CheckoutSession*Request/order_notes`、`Order/client_reference_id`、`PaymentHandler/display_order`、`Error/supported_versions`），同时要求 `known-property-drift.txt` 在问题修复后若仍残留陈旧条目必须触发验证失败（防止技术债白名单只增不减）。
   - **`allOf` + `additionalProperties: false` 兄弟分支饥饿陷阱（`#290`、`#275`）**：在 JSON Schema Draft 2020-12 / OpenAPI 3.1 中，`additionalProperties: false` 仅识别**同一 Schema 对象内部**声明的 `properties`，看不见兄弟 `allOf` 分支新增的属性。因此 `CheckoutSessionWithOrder = allOf[CheckoutSessionBase, {order}]`（`#290`）与 `DelegateAuthenticationSessionWithResult = allOf[DelegateAuthenticationSessionBase, {authentication_result}]`（`#275`）会导致任何携带 `order` 或 `authentication_result` 的合法响应被基底 Schema 的 `additionalProperties: false` 拒绝。
   - **OpenAPI 手写缩进错位（`#284`）**：`PaymentHandler.display_order` 在 `openapi.agentic_checkout.yaml` 中被错误缩进到与 `properties:` 同级，被解析器当作未知关键字静默忽略，进而导致所有携带 `display_order` 的支付处理器对象被 `additionalProperties: false` 拦截。

### 2.3 Google AP2 (`google-agentic-commerce/AP2`) & Personal Agent Protocol (`Poppy v0.2`)
1. **AP2 PR `#369`（`test(ap2): add mandate conformance corpus and reference verifier`，`2026-10-20` 更新）与 `poc_aud_not_enforced.py` 终端受众绕过漏洞**：
   - **跨语言合规语料库缺口**：目前 AP2 生态中仅 Python SDK 具备真实签名/验签能力，Go 示例硬编码 `FakeJWT = "******"`，导致 `Universal-Commerce-Protocol/conformance` 无法执行正向测试。PR `#369` 首次提供跨币种（USD/BRL）字节级签名测试向量。
   - **`kb+sd-jwt+kb` 受众（`expected_aud`）静默失效漏洞（`poc_aud_not_enforced.py`）**：`ap2.sdk.sdjwt.kb_sd_jwt.verify` 仅当 `typ in TYP_TERMINAL`（`['kb+sd-jwt', 'kb-sd-jwt']`）时才调用 `common.verify_expected_claims(expected_aud, expected_nonce)`。然而当载荷包含 `cnf` 声明时，SDK 生成的令牌类型为 `kb+sd-jwt+kb`（落入 `TYP_INTERMEDIATE`），导致即使商户显式传入 `expected_aud="https://honest-merchant.example/ap2"`，攻击者签发给 `https://attacker.example/ap2` 的委托链也能毫无阻碍地通过验证（`VERDICT: DEFECT CONFIRMED`）！
2. **AP2 PR `#385` / `#383`（`cnf.jwk` JSON 模式枚举序列化）与 PR `#384`（`verify_receipt` 空回调防护）**：
   - `ParsedToken.cnf_jwk` 调用 `model_dump(exclude_none=True)` 时未传 `mode="json"`，导致 `use="sig"` 保留为 Python `Use.sig` 枚举实例而非字符串，传入 `jwcrypto.jwk.JWK` 时触发 `InvalidJWSSignature`（`#385`/`#383`）。
   - `ReceiptClient.verify_receipt` 中 `has_reference_in_store_cb` 默认为 `None`，却被无条件调用导致 `TypeError: 'NoneType' object is not callable`（`#384`）。
3. **Poppy `v0.2` Commit `39b35bd`（`Make examples and guides match the spec (#71)`）**：
   - 明确 §4.3 DPoP 证明规则：发往令牌端点的每个请求与携带 Session Token 的每个请求都必须附带 `ES256` 签名的 DPoP Proof（`jti` 至少 128 bits 熵，如 `e1j3V_bKic8-LAEBq7Rw2g`）；**唯一例外**是为仅支持 Bearer 的 MCP Server 请求 Bearer Token，以及既不发往令牌端点也不携带 Session Token 的请求（§4.9 令牌吊销与 §4.6 设备授权）。所有 API 写操作（如 `POST /orders/.../exchanges`）必须携带 `Idempotency-Key`。

   - 新增 **$\tau$-entity 外呼实体采集域（`intake` domain，`data/tau2/domains/intake/agent_directed_policy.md` & `ENTITY_PROVENANCE.md`）**：定义多租户服务局（诊所、汽车维修、酒店集团）外呼补全缺失表单字段的六大硬性纪律：
     1. **先同意后询问（Consent-Before-Collection）**：接通后必须先点明表单所属人姓名与委托机构并征得受访者同意，获得肯定答复前严禁询问任何缺失字段；
     2. **最小范围采集（Scoped Minimization）**：仅采集工单 `missing_fields` 列出的字段，严禁越权索取额外字段或使用通话外/编造数据；
     3. **静默工具与强制预记录（Silent `log_capture`）**：严禁向用户口播内部工具或系统查询过程，每个采集到的字段必须在提交前通过 `log_capture` 记录；
     4. **校验位与格式精算**：车辆 VIN 校验位、会员号 `mod-97` 校验（`int(digits) % 97 == 1`）、日期 `YYYY-MM-DD` 与时间 `H:MM AM/PM` 格式必须精确合规；
     5. **单次提交与提前挂断零提交**：所有缺失字段汇总为**唯一一次** `submit_fields` 调用；若受访者提前挂断，严禁提交半成品记录；
     6. **提交与挂断轮次物理隔离（Turn Separation）**：`submit_fields` 必须在独立轮次调用并等待返回成功后，才能在下一轮次调用 `end_call` 道别，严禁在同一轮次并发调用 `submit_fields` 与 `end_call`。
2. **Visa Trusted Agent Protocol PR `#11`（`Feat/x402 implementation`）**：
   - 在 TAP 商户后端与 CDN 代理中集成基于 **Solana (`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`) 与 Base Sepolia (`eip155:84532`) USDC** 的机器对机器 `x402` 结账流程：Mode A（无 `PAYMENT-SIGNATURE` 头）返回 HTTP `402` 与 `PAYMENT-REQUIRED` 头；Mode B（携带 `PAYMENT-SIGNATURE` 头）通过 Facilitator 完成链上原子结算、校验购物车 `subtotal + tax + shipping == total_amount` 守恒并返回 `PAYMENT-RESPONSE` 头。

## 3. 辩证架构思考：AI-Native 架构 vs. 云厂商经典三层 Web / Well-Architected 架构

| 维度 | 云服务商经典三层 Web / WAF 假设 | Agentic Commerce AI-Native 确定性架构改进（Stage 54 落地） |
|---|---|---|
| **契约与 Schema 演化** | 人工维护 OpenAPI 供前端阅读，小幅字段偏差靠前端容错 | 机器 Agent 严格依赖代码生成与结构化校验；必须通过双源属性漂移检测（ACP `#310`）、消除 `allOf` + `additionalProperties: false` 兄弟分支饿死（`#290`/`#275`）并恢复打包 Schema `$ref` 拓扑（UCP `#982`） |
| **展示元数据 vs. 信任权威** | 页面显示商家 Logo 即代表平台背书 | 严格分离展示层媒体（`seller.logo`，UCP `#962`）与 `/.well-known/ucp` 密码学发现权威，阻断视觉/名称仿冒提权 |
| **多层委托链验签** | OAuth JWT 单跳验签，假定 SDK 默认校验 `aud` | 针对携带 `cnf` 的 `kb+sd-jwt+kb` 令牌（AP2 `#369` `poc_aud_not_enforced.py`）在终端跳强制执行独立于 `typ` 分类的 `expected_aud`/`expected_nonce` 门禁，并强制 `cnf.jwk` JSON 模式序列化（`#385`/`#383`） |
| **语音/多语种外呼交互状态机** | LLM 自由对话并在结束时打包调用多个工具 | 遵循 Sierra $\tau$-bench 2.0.0 `intake` 确定性状态机：先征得同意 $\rightarrow$ 限定字段采集 + `mod-97`/ISO 格式校验 $\rightarrow$ `log_capture` $\rightarrow$ 独立轮次单次 `submit_fields` $\rightarrow$ 严禁与 `end_call` 同轮并发 |
