## 2. 2026-10-21 一手协议规范与代码库审计发现（Stage 116）

### 2.1 Agentic Commerce Protocol (`agentic-commerce-protocol/agentic-commerce-protocol`)
1. **PR `#316`（commit `2b2f2dd`，`2026-10-21T15:12:30Z`）：`SEP #303: UserApproval and approval_digest bind what the user approved to the checkout (Section 4.4a, rule 4)`**：
   - **问题背景**：在 Agent 代理结账场景中，当用户向发卡行或争议裁决方主张“Agent 下单的款式/数量不是我批准的”（例如用户批准了 `TEE-01` 的 `green` 款，但 Agent 实际向商家下单了 `black` 款）时，若仅凭争议发生后 Agent 平台单方面提交的审批记录，无法证明该审批在结账完成时真实存在且未被事后篡改；反之，若直接对商家执行拒付（Chargeback），则会让完全按 Agent 确认指令履约的无辜商家背锅。
   - **密码学承诺与双态核验（Section 4.4a）**：
     - 新增 `UserApproval` 结构：包含 `items[]`（每项必填非空 `sku`、整数 `quantity >= 1`、可选 `variant`）、`approved_at`（RFC 3339 时间戳）以及 `approval_digest`（`^[0-9a-f]{64}$`，即对 `{items, approved_at}` 执行 RFC 8785 JCS 规范化后的小写十六进制 SHA-256 摘要）。
     - 在 `CheckoutSessionCompleteRequest.dispute_resolution` 上新增可选 `approval_digest`，使商家在任何争议发生前即持有结账完成时的用户审批摘要承诺。
     - 在 `DisputeRecord` 上新增可选 `user_approval`。争议裁决方（Dispute Provider）**必须**对 `{items, approved_at}` 重新计算 RFC 8785 JCS SHA-256 摘要，并同时校验其等于 `user_approval.approval_digest` 且等于结账完成时商家收到的 `approval_digest`。只有同时通过这两项校验的 `user_approval` 才具备可采信证据效力（否则仅视为平台的单方面陈述）。
   - **意图冲突归责（Section 7.4 Rule 4）**：当 `user_approval` 通过 Section 4.4a 校验，且争议订单行的 `sku`、`variant` 或 `quantity` 与用户批准的条目不一致时，裁决引擎将该争议记录为针对 **Agent 平台（`agent_platform`）** 的 `intent`（意图）冲突裁决，**不撤销商家收款（`merchant_charge_reversed = False`）**，因为商家忠实履行了 Agent 确认的订单。

   - **准入单次评估（Evaluate-Once-at-Admission）**：明确 AP2 授权存活期（`evaluated_at <= mandate_exp`）在 `Complete Checkout` 准入时**仅评估唯一一次**。一旦准入时刻未过期（`result == "VALID"`），授权在整个结账完成生命周期内冻结——即便异步支付处理（`complete_in_progress`）结束时 `completed_at > mandate_exp`，商家也**严禁**中途以 `mandate_expired` 终止结账；若准入时刻已过期（`evaluated_at > mandate_exp`），则立即置为 `canceled` 并返回 `mandate_expired` 与签名收据 `{reference, checkout_id, evaluated_at, mandate_exp, result: "MANDATE_EXPIRED"}`。
   - **密钥发现收敛（`207314b`）**：废除单独的 `signing_keys[]` 表述，统一复用 AP2 Mandates 扩展的 `/.well-known/ucp` `keys[]` JWK 发现机制（ES256 必选，ES384/ES512 可选，RFC 8785 JCS 规范化）。
3. **PR `#966`（`2026-10-21T07:45:13Z` 更新）：`dev.ucp.shopping.policy.return` 显式退货资格、商家直报截止日与类型化退货费上限**：
   - **显式退货资格**：`eligibility` 必须显式取值为 `window`、`unlimited` 或 `not_accepted`（省略不代表无限期退货；特定商品条件视为资格前置要求）。
   - **禁止平台侧推算截止日**：退货截止时间 `expires_at` 必须由商家直接声明（解析订单创建时的政策快照，并妥善处理分批履约的保底截止期），严禁 Agent 平台根据 `duration` + `anchor` 自行计算日期；锚点收敛为 `purchased` | `fulfilled` | `delivered`。
   - **类型化退货费上限**：`fees[]` 作为估计上限（固定 `amount`、`basis_points` + `max_amount`，或无类型 `{amount: 0}` 表示免退货费），商家实际收取的退货费严禁高于声明值。

## 3. 辩证架构思考：AI-Native 架构 vs. 云厂商经典三层 Web / Well-Architected 架构

| 维度 | 云服务商经典三层 Web / WAF 假设 | Agentic Commerce AI-Native 确定性架构改进（Stage 116 落地） |
|---|---|---|
| **用户审批与订单争议归责** | 人类点击结账即代表完全知情同意，争议一律按商家拒付（Chargeback）处理 | Agent 存在意图偏离风险；必须在 `Complete Checkout` 时锚定 `UserApproval` 的 RFC 8785 JCS SHA-256 `approval_digest`（ACP `#316`），当通过双态核验的审批与 Agent 下单内容冲突时归责 `agent_platform` 而非撤销商家收款 |
| **委托授权 TTL 与退货期限权威** | 每次内部微服务调用重复校验会话过期；前端自行按天数计算退货截止日 | AP2 授权 TTL 在 `Complete Checkout` 准入时**单次评估并冻结**（UCP `#540` `207314b`），防止长耗时清算中途流产；退货 `eligibility` 必须显式声明且由商家直报 `expires_at`（UCP `#966`） |
| **API 付费墙与返回结果可验证性** | HTTP 200 即视为交付完成，路由解码与中间件匹配假定一致 | 引入 `x402` `response-provenance` 五元组 JCS SHA-256 摘要与三态不坍缩验证（`#3304`），转义内联配置 `<` 防 XSS（`#3855`），并双视图匹配 `%2F`/`%5C` 防付费墙绕过（`#3857`） |
| **Agent 知识库沙箱隔离** | 黑名单正则过滤命令行文本即可防止越权读取 | 正则剥离引号会被 `python3 -c` 绕过；必须实施最小环境变量白名单 + 输出密钥脱敏（$\tau$-bench `#653`）与根路径遍历 `denyRead` 读白名单模拟（`#655`） |
