# 2026-10-10 · Agentic Commerce 架构研究

**研究日期：** 2026-10-10，Asia/Shanghai。**性质：** AI 辅助的原创技术研究；来源为公开官方公告、当前开发文档和参考仓库。本次核验不是对全部互联网发布的穷尽检索，也不构成产品认证或支付、法律合规意见。

## 今日结论

Agentic Commerce 不是“给 LLM 一个支付工具”。它需要将意图理解、商业交互、代理身份、用户授权、支付凭证、订单履约和交易恢复拆成独立边界。**模型负责建议；确定性系统负责授权与执行。** Visa 与 Stripe 既有不同切入点，也有互补和重叠产品，不适合简单画成竞品二选一。

Visa Intelligent Commerce 从支付网络、tokenization、用户控制和合作伙伴能力切入；TAP 从商户入口的 Agent 信任切入；Intelligent Commerce Connect 又延伸到 Acceptance Platform 的多协议、多 token vault 接入。Stripe ACP 定义商业交互，Suite 降低商户接入多 Agent 的复杂度，SPT 承载受限支付凭证，Link 提供消费者控制的钱包，MPP 服务无 checkout UI 的机器付费。[visa-intelligent-commerce-launch][visa-commerce-connect][stripe-acp-docs][stripe-spt][stripe-mpp]

## 协议层次和标准成熟度

| 层次 | 对象 | 核心职责 | 不应误认为 |
| --- | --- | --- | --- |
| Agent 工具与协作 | MCP、A2A | 工具调用/上下文接口、Agent 间协作；UCP 可选择相关 binding | 用户同意、支付网络或任意动作的合法授权 |
| 商业交互 | ACP、UCP | capability、商品/购物车、checkout、付款处理器、订单生命周期 | 消费者钱包、支付处理器或全球监管认可 |
| 委托与证据 | AP2 | 签名 Intent/Cart Mandates，建立用户意图和批准的证据链 | 自动免除拒付责任，或任意购物车的授权 |
| 入口信任 | TAP | Agent 身份、merchant/purpose/time-bound 签名及 replay/relay 防护 | 仅凭 User-Agent 字符串放行；checkout API 或支付清算 |
| 受限凭证 | Stripe SPT、网络 tokenization | 降低原始凭证暴露，限制凭证用途 | 仅因 token 被持有就可以购买任何商品 |
| 机器资源付费 | MPP、x402 | HTTP 402 场景下的付费访问；Stripe 文档分别提供两条集成路径 | MPP 与 x402 同一 wire format，或完整零售订单管理 |

ACP 官方仓库当前 README 标记 **beta**，采用日期版本；本次观察到 `2026-04-17` 快照，以及独立的 `unreleased` 目录。实验设计应固定日期快照，不能把 `main` 或 `unreleased` 当成稳定生产契约。Stripe ACP 文档列出 Stripe、OpenAI、Meta；仓库治理说明以 OpenAI/Stripe 为 founding maintainers。**合作伙伴描述与治理主体不是同一事实。** [acp-spec][stripe-acp-docs]

UCP 官方技术文章描述 `/.well-known/ucp`、capabilities/extensions、payment handlers 以及 API/MCP/A2A binding；AP2 公告明确 human-present 场景中确认 Cart Mandate，human-not-present 场景中先签具备条件的 Intent Mandate。这些是互补边界，不是将所有协议串成固定强依赖。[google-ucp][google-ap2]

## 解决方案架构师判断

商户优先：已有 Stripe 商户先评估 Suite + ACP/UCP adapter，保留库存、税、运费、订单系统及 Merchant of Record 责任；已有 Visa Acceptance Platform 或多网络支付需求，评估 Connect 的实际接入资格。不要在产品未获资格时用 mock 结果宣称集成成功。

Agent 平台优先：采用独立 consent/policy service 和受限 credential broker；TAP verifier 放在商户/CDN 信任边界；checkout adapter 与 payment adapter 分离；human approval 绑定 merchant、商品、数量、最终总价、币种、期限和 quote fingerprint。SPT 只解决部分支付授权，**商品限制仍需应用策略层**。

API monetization 优先：MPP/x402 更贴近按请求访问服务；除了支付还需资源 entitlement、重试幂等和 receipt 绑定，避免付款成功但资源重复计费或无法交付。卡费率和最小额决定是否需聚合计费，不能由模型自行循环创建微交易。

证据登记把 announcement、documentation、specification、reference_code 分开。TAP 样例 revision 为 `16d59bdf3f8a542bc538d0962edbb80ea30a02af`；ACP 仓库 revision 为 `7fdd78df677a94dce04c770644b0fbbb1401272b`。这些 commit 是本次 API 查询得到的代码锚点；厂商 live docs 不保证能按历史日期回放，后续会变动。
