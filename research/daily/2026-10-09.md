**视角：解决方案架构师。** 本日建立首份公开证据基线，不声称这些产品均于今日发布，也不声称穷尽截至今日的全部发布。复核时区为 Asia/Shanghai。来源编号、原始链接、发布日期、API 版本和代码 revision 见 [来源登记表](../sources.json)。

## 核心结论

Agentic Commerce 的关键不是“让模型能调用付款工具”，而是把商业意图、用户授权、商户报价、支付凭证、交易结果分开治理。可信 Agent 身份不等于用户同意；用户同意不等于银行授权；银行授权不等于捕获、结算或履约。

Visa 与 Stripe 不是简单替代关系。Visa Intelligent Commerce（VIC）偏向网络凭证、用户支付指令与网络级约束；TAP 偏向商户入口的 Agent 可信交互。Stripe ACP 与 Suite 偏向商业交互与商户接入，SPT 偏向范围受限的凭证交付。Stripe 当前 SPT 文档明确提到可能使用 VIC/Agent Pay 网络 token，说明两层可以组合，但不能推断所有账户已经获得该能力。[S02, S04, S07, S11]

## Visa 深入观察

VIC 开发者描述的链路为 onboarding → agent-specific token provisioning → 用户同意 payment instruction → passkey 认证 → 按指令请求凭证 → 购买 → VisaNet 商户/金额控制 → 反馈 commerce signals。[S02]

架构含义：将用户认证放在可信 UI，将指令存放于确定性授权服务，凭证留在隔离执行层。保留“同意了什么、最终报价是什么、提交了什么、网络反馈是什么”的关联证据，才能处理争议。文档描述的初始 guest checkout/form fill 不应被解释为任意网页自动化都可信。

TAP 的 HTTP 签名与可信公钥来源应在商户入口或 CDN 验证，执行目标域名、动作、有效期及 replay 检查。RFC 9421 是基础签名标准，TAP 是商业上下文约定，二者不是同一个标准。支付凭证仍需要独立授权；不因签名有效就跳过风控或追加消费者身份数据。[S03–S05, S21]

Connect 可以作为商户/enabler 接入选项，但 pilot 公告不足以证明本账户有生产权限或每种协议等价支持。接入前需获得地区、卡种、token vault、协议版本、PCI 责任及 dispute 流程的明确契约。[S06]

## Stripe 深入观察

ACP 是开放商业交互契约；Suite 是 Stripe 的集成产品。对多渠道销售，不要只实现支付 API：产品目录、报价更新、库存、运费、税、消费者 action、订单反馈和退货都属于端到端方案。[S07–S10, S15, S16]

SPT 当前文档的 Agent 示例使用 `2026-09-30.preview`，绑定 seller profile、币种、最大金额与到期时间，支持撤销和 `requires_action`。需先判断 Agent 接入资格及地区，不在可用地区列表中不能用“公开文档存在”代替授权。`active` 只是 token 可用，不代表 PaymentIntent 成功。[S10, S11]

Link Agent Wallet 使用 `api.link.com` 与消费者 OAuth，不是 `api.stripe.com` 加 Stripe secret key。支付能力面向美国/加拿大客户，financial insights 面向美国客户；可用地区、敏感数据接收责任与 scope 应独立审查。[S12]

Stripe 开发工具应从当前 agents/plugin/MCP/skills 入口发现，而不是把历史 toolkit 名称当成冻结 API。MCP 提供资源操作能力，不会自动构成消费者付款委托。当前文档特别提醒 **2026-10-31** 起不接受 full-access secret keys 和无 Agent 标记的 restricted keys；这是未来截止日，不是本日已发生的变更。[S13, S14]

MPP 面向 API、工具、数据等机器付费，HTTP 402 → challenge → 付款凭证 → 验证 → receipt。Stripe 文档所列卡支付最低 USD 0.50、stablecoin 最低 0.01 USDC 是本次观察，不是永恒参数。不能照搬“每 token 卡支付”，应评估 session/聚合计费与资金/费用模型。[S17, S20]

## 场景优先级与验收

| 场景 | Agent 职责 | 确定性控制 | 商业验收建议 |
|---|---|---|---|
| 人在场的个人购物 | 搜索、比较、推荐、组购物车 | 最终含税/运费报价批准；支付 challenge 交回用户 | 购买转化率、错误购买率、审批耗时 |
| 无人在场的补货 | 根据明确委托触发需求 | 指定 SKU/替代规则、商户、累计预算、期限、撤销 | 缺货率、越权率必须为 0、预算消耗 |
| 差旅与酒店预订 | 比较行程和取消条款 | 预授权/押金/最终金额分开批准；变价重新同意 | 变价率、退改成功率、人工介入率 |
| B2B 采购 | 供应商比较、报价整理、申请订单 | 企业审批链、采购单、税票、供应商白名单 | 采购周期、三单匹配率、审计完整度 |
| Agent 付费 API | 选择数据/工具、消费资源 | 402 验证、单次和累计限额、receipt 对账 | 单任务成本、成功交付率、重复收费率 |
| 售后 Agent | 查询物流、申请退款、处理换货 | 订单授权和退款权限分离，不允许自行改收款人 | 退款到账时间、争议处理时长 |

以上为**方案建议**，不是供应商承诺。先实现人在场购物；长期委托、BNPL、差旅和跨商户组合交易需要独立授权模型，不能由单笔 demo 推广。
