## 4. AI Native workload：领域不变量补强，不推翻 WAF

通过 Microsoft Learn search 后读取[官方 WAF AI application design 正文](https://learn.microsoft.com/en-us/azure/well-architected/ai/application-design)，并只读发现 Azure WAF 工具能力，没有查询账户或操作资源。官方已包含 Client / Intelligence / Inferencing / Knowledge / Tools 五层、工具自己执行策略、确定性编排、AI-aware caching 与版本管理；不能假称云厂商仍只给“三层 Web”。[N-tier](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier)是架构风格，WAF 是质量与取舍框架，二者不能等同。

结合今日新增核验的 **Sierra 四层运行时防线（Content → Rules → Supervisors → Deterministic Guards）**、**Sierra Level 1 PCI 支付旁路**、**Poppy `v0.1` 的 DPoP/MCP-Bearer 双轨令牌与 `operations` 两阶段修订确认**，以及 **$\tau^2/\tau^3$-bench 的目标 DB 状态哈希评测（`reward_basis=["DB","COMMUNICATE"]`）**，AI-Native Agentic Commerce 架构对经典三层 Web 与通用云 WAF 的核心演进可以进一步收敛为：

**本研究的核心设计主张：允许 Agent 的探索路径变化，但不允许它扩大经济权限、在 LLM 上下文中裸奔持卡人数据（CHD），或把自然语言对话/证据缺口解释成交易确认。** 以下是方案建议，不是供应商认证要求。

| 重新思考的设计面 | 保留 WAF/传统工程能力 | Agentic Commerce 必须明确的补强与取舍 |
|---|---|---|
| 信任边界与身份拓扑 | IAM、API gateway、职责分离 | 推理/建议面、可信授权/确定性执行面、经济状态/证据面逻辑分离；Poppy 会话令牌（DPoP 或单 MCP 绑定的 Bearer）、MCP identity、TAP authenticity、consumer consent、PSP result 不能互相替代；单会话强制绑定单一客户账户（`account_mismatch` 阻断跨户查询） |
| 契约正确性与跨域防伪 | 固定版本 OpenAPI/schema、兼容性测试 | 基础 capability + negotiated extensions + 双向域名/签发者验证（如 Poppy `auth.issuer` 与 OAuth metadata `poppy_domains` 互验）+ 语义约束分别验证。UCP 上游漏检证明基础 parse pass 是弱信号 |
| 工具可见性与行动空间 | 最小权限、RBAC、审批 | 遵循 Sierra MCP Gateway 原则（"An agent can't misuse what it never sees"）：未完成客户鉴权或缺少 `poppy:write` 时，修改类工具对模型不可见或确定性拦截；通用 `stripe_api_write` 不能靠 prompt 限制 |
| 可变推理与两阶段固定批准 | 配置版本、缓存、DDD | 借鉴 Poppy `operations` v1 与 ACP/SPT：修改/换货/扣款工具先返回不可变 `revision` 的 `proposed` 操作，仅由独立确认端点针对最新 `revision` 执行（若条款变更则返回 `terms_changed`）；**对话消息（即使 `sender: "human"`）绝不触发确认** |
| PCI / 敏感凭证旁路与双速交互 | TLS、合规隔离区、前端表单 | 借鉴 Sierra Payments（Visa Level 1 PCI）与 Tandem Voice：收集支付凭证时切出 LLM 循环，由服务端预定义序列直传 Stripe/PSP，LLM 只收状态与后四位；实时语音拆分为快 Conversation 层与慢 Reasoning 层 |
| 领域状态机与异步经济结果 | 幂等、outbox、saga、对账 | 借鉴 $\tau^3$-bench 零售策略与 SABER：待发货订单商品修改仅限一次（`pending (items modified)` 锁定后续修改/取消）、同商品不同规格校验、仅退回原支付方式或礼品卡；`unknown` 保留预算并先查询对账，不换 key 重复扣款 |
| 证据、评测与规则演进 | 配置审阅、变更控制、CI/CD | 借鉴 Sierra Release Governance（Agent Checks 静态检查 + Simulations + 审批流 + Split-traffic 灰度）与 $\tau^3$-bench 目标 DB 哈希评测：评判标准是最终确定性业务库状态（DB Hash）与合规沟通，而非单条固定 tool call 轨迹 |
| SLO 与成本 | Availability/latency/cost、运维追踪 | 加上正确交易完成、授权符合、重复经济副作用、unknown backlog 和每成功订单总成本；区分推理时间、人工批准、付款确认和履约。模型 tokens/HTTP 200 不是商业成功指标，本轮不捏造线上数字 |

新增证据尤其要求 adapter 的验证分级：**可解析 → 双向域名/扩展兼容候选 → 会话与写权限门控 → 两阶段修订确认（`operations` / Mandate）→ PSP/network 可信结果**。
