## 4. AI Native workload：领域不变量补强，不推翻 WAF

通过 Microsoft Learn search 后读取[官方 WAF AI application design 正文](https://learn.microsoft.com/en-us/azure/well-architected/ai/application-design)，并只读发现 Azure WAF 工具能力，没有查询账户或操作资源。官方已包含 Client / Intelligence / Inferencing / Knowledge / Tools 五层、工具自己执行策略、确定性编排、AI-aware caching 与版本管理；不能假称云厂商仍只给“三层 Web”。[N-tier](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier)是架构风格，WAF 是质量与取舍框架，二者不能等同。

**本研究的核心设计主张：允许 Agent 的探索路径变化，但不允许它扩大经济权限或把证据缺口解释成成功。** 以下是方案建议，不是供应商认证要求。

| 重新思考的设计面 | 保留 WAF/传统工程能力 | Agentic Commerce 必须明确的补强与取舍 |
|---|---|---|
| 信任边界 | IAM、API gateway、职责分离 | 推理/建议面、可信授权/确定性执行面、经济状态/证据面逻辑分离；MCP identity、TAP authenticity、consumer consent、PSP result 不能互相替代。隔离成本增加但降低模型错误的经济爆炸半径 |
| 契约正确性 | 固定版本 OpenAPI/schema、兼容性测试 | 基础 capability + negotiated extensions + 方向/操作 + 语义约束 + 密码学/商业授权分别验证。UCP 上游漏检证明基础 parse pass 是弱信号；未知扩展拒绝或隔离会牺牲覆盖率，但避免权限提升 |
| 工具的行动空间 | 最小权限、RBAC、审批 | 通用 `stripe_api_write` 不能靠 prompt 限制；执行边界校验 method/route/object/金额/环境/批准范围。Agent 不可批准自身提出的动作，不能把“允许调用工具”当“允许此次交易” |
| 可变推理与固定批准 | 配置版本、缓存、DDD | approved binding 包含最终购物车、收款方、费用、币种、条款、时限与版本；价格/工具/政策改变后不得沿用旧批准。探索可重试，经济副作用重试必须绑定原请求与持久状态 |
| 异步经济结果 | 幂等、outbox、saga、对账 | `unknown` 保留预算 reservation，查询已有交易，不换 key 再扣款；token consumed 不等于 paid；refund requested 不等于到账；外部资金不能靠本地 SQL rollback 撤回。等待对账增加时延但避免重复扣款 |
| 证据与规则演进 | 配置审阅、变更控制、CI | 来源指纹、选定事实、语义审阅、规则变更、实际账户验证分开。新监测字段只产生 review 信号，绝不自动创建凭证或把官网指导变成权限 |
| SLO 与成本 | Availability/latency/cost、运维追踪 | 加上正确交易完成、授权符合、重复经济副作用、unknown backlog 和每成功订单总成本；区分推理时间、人工批准、付款确认和履约。模型 tokens/HTTP 200 不是商业成功指标，本轮不捏造线上数字 |
| 部署粒度与降级 | 模块化单体、受控服务拆分、bulkhead | 优先在现有应用实现逻辑边界；按真实合规/独立扩缩容需要拆分。模型 failover 可以更换推理后端，付款路径不能静默换卡/商户/handler；不可验证时解释并转人工，而非自动扩大权限 |

新增证据尤其要求 adapter 的验证分级：**可解析 → 可执行兼容候选 → 消费者授权 → PSP/network 可信结果**。扩展 AP2 字符串符合 JOSE 格式，仍不证明签名、issuer/audience、有效期、nonce 和最终 quote binding 有效；文档 header 表完整，也不证明账户权限或商业资格存在。

| 场景 | 今天的增量价值 / 方案 | 必须保留的停止条件 |
