## 2. 辩证架构思考：AI-Native 交易工作负载架构 vs. 云厂商经典三层 Web / Well-Architected 架构

| 维度 | 云服务商经典三层 Web / WAF 架构 | Agentic Commerce AI-Native 架构改进 |
|---|---|---|
| **预授权状态与实际准入溯源** | 经典三层架构通常将“订单/审批状态（`active`）”与“请求是否已进入下游执行管道”混在同一张业务主表或缓存字段中，排障时无法区分“从未尝试准入”与“曾尝试准入但参数被篡改”。 | 将静态审批策略表（`payment_approvals`，通过 `read_approval` 观测）、首次过闸时间证据表（`payment_admissions`，通过 `find_admission` 观测）与执行尝试账本（`payment_attempts`，通过 `read_attempt` 观测）三表分离，共享同一 SQLite 事务边界但不回填历史。 |
| **只读观测与异常语义消歧** | 常以单一业务异常笼统表示“记录未找到或校验失败”，导致调用方依赖异常字符串匹配。 | Stage 1729 新增 `PaymentApprovalStore.find_admission(operation) -> ApprovalAdmission | None`，Stage 1730 新增 `MerchantSignerStore.find_timed_admission(operation) -> TimedSignerAdmission | None`：无记录或走非计时准入路径返回 `None`，而 10 维操作指纹不一致或持久化元数据损坏则显式抛出异常。 |
| **可信时钟采样位置** | 在 Web API 网关入口取一次请求时间戳并透传。 | 只读查询（`read_approval` / `find_admission` / `read_permission` / `find_timed_admission` / `read_attempt`）零写锁、零时钟采样；唯有写路径 `admit()` 在获取 `BEGIN IMMEDIATE` 写锁后采样可信时钟并持久化 `admitted_at`。 |
