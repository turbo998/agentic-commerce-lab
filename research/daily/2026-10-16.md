### 2.2 Sierra 与 Personal Agent Protocol（Poppy `v0.1` 草案）：17 个规范提交补齐安全考量、DPoP RFC 9449 对齐与会话持久化绑定

`personal-agent-protocol/personal-agent-protocol` 仓库自 `2026-10-14T15:35:49Z`（`f766ef8b`）至 `2026-10-16T13:19:34Z`（`e910c866`）共合入 **17 个提交**，显著收紧了个人 Agent 与企业服务端之间的安全边界：

1. **发现文档 `organization.domain` 严格匹配重定向后主机（`#37`，`efc12168`，2026-10-15）**：
   - 规范第 2.1 节更新为：`organization.domain` **必须**是跟随所有重定向后实际提供 `poppy.json` 的主机名，**仅按忽略大小写比较，不再剥离前导 `www.`**；第 3.3 节 OAuth 元数据中的 `poppy_domains` 同样按仅忽略大小写包含 `organization.domain`。
2. **DPoP 与 RFC 9449 全面对齐及端点差异化状态码（`#36`，`46dafba3`，2026-10-15）**：
   - OAuth 元数据必须发布 `dpop_signing_alg_values_supported` 且必须包含 `"ES256"`。
   - 服务端校验 DPoP Proof 时必须验证 `typ == "dpop+jwt"`、`alg` 属于已声明支持集合且不为 `"none"`、`jwk` 仅含公钥字段，以及服务端下发的 `DPoP-Nonce`（不匹配返回 `use_dpop_nonce`）。
   - `jti` 重放检测在令牌端点为强制（`MUST`），在 API 与会话端点为可选（`MAY`，状态变更请求依赖幂等机制）。
   - **状态码区分**：DPoP 错误（`invalid_dpop_proof`、`use_dpop_nonce`）在令牌端点返回 **HTTP `400`**，在 API、会话及操作端点返回 **HTTP `401`**（附 `WWW-Authenticate: DPoP`）。
3. **客户端与会话断言 `aud` 强制绑定 `auth.issuer` 防跨企业重放（`#50`，`483c3cea`，2026-10-16）**：
   - 第 4.1 节（`private_key_jwt` 客户端认证）与第 4.2 节（`jwt-bearer` 会话断言）明确要求 `aud` 必须设为企业 `poppy.json` 中的 `auth.issuer` **单一字符串**（严禁设为 `token_endpoint` 或数组，对齐 `draft-ietf-oauth-rfc7523bis`）。
   - **安全机理**：防止恶意企业将自身 OAuth 元数据中的 `token_endpoint` 指向另一家诚实企业，从而重放个人 Agent 发送给恶意企业的断言。
4. **Session 账户绑定跨越登出持久化（`#41` `8695a365`、`#49` `0166922c`）与受托登录吊销后禁止自动重登（`#40` `51dfab56`、`#53` `37d1a13c`）**：
   - Session 一旦登录某个用户账户，**即使调用登出端点（4.9）回到未登录态，该 Session 仍永久绑定该账户**；后续在同一 Session 上通过任何登录方式（`direct`、`device`、`mediated` 或 `account_token`）尝试登录另一账户，均必须返回 HTTP `400` `account_mismatch`。
   - 受托登录（Mediated Sign-In）状态机补齐错误码（`invalid_scope` 400、`account_mismatch` 400、`sign_in_not_found` 404），并规定登录结束后个人 Agent 必须丢弃凭证或仅保存在用户选择的凭证库中（严禁留在模型上下文或日志中）；当用户或企业吊销该登录态后，**未经用户显式发起新登录，个人 Agent 严禁使用已存凭证自动重新登录**。
5. **新增第 8 节《Security considerations》与 `operations` 摘要-条款一致性校验（`#51`，`e910c866`，2026-10-16）**：
   - **8.1 来自企业的内容视为不可信数据**：会话消息、API/MCP 描述与返回结果、网页内容及操作 `summary` 均可能包含恶意指令（Prompt Injection）。个人 Agent **严禁**因为企业 A 的内容要求而操作企业 B 或向企业 B 发送数据，且每次仅向企业发送当前任务所需的最小上下文。
   - **操作提案 `terms` 与 `summary` 对齐（`operations.mdx` & `8.1`）**：由于操作修订版的自然语言 `summary` 与结构化 `terms` 均由企业生成，个人 Agent 在请求用户批准前，**应当（SHOULD）向用户展示关键 `terms` 字段（金额、日期、商品项）或校验其与 `summary` 一致**，防止 `summary` 虚报低价或错误标的诱导用户授权。

### 2.3 Universal Commerce Protocol（UCP）：订单 Webhook 签名门禁破坏性修复（`#659`）与条件请求 `304` 规则（`#933`）

`Universal-Commerce-Protocol/ucp` 官方仓库在 `2026-10-14` 至 `2026-10-16` 期间合入 **4 个提交**（`e45c0212` $\rightarrow$ `5021fa83`）：

1. **`69e28f4fb781`（2026-10-16T07:23:33Z，`#659`，`fix(order)!: cover webhook-id and webhook-timestamp in the signing gate`，BREAKING CHANGE）**：
   - **漏洞根因**：此前 UCP 将订单 Webhook 的 `event_id` 与 `created_time` 从 JSON Body 移入 HTTP 头 `Webhook-Id` 与 `Webhook-Timestamp`，导致这两个字段不再受 `Content-Digest` 保护；若不强制纳入 RFC 9421 签名覆盖集，事件标识与事件发生时间将在传输中处于未签名状态。
   - **规范修复**：将 `webhook-id` 与 `webhook-timestamp` 正式加入 UCP 身份解析与认证（IRA Step 5）及 `signatures.md` 的**闭合“存在即必签（sign-if-present）”覆盖组件集**（必签派生组件 `@method`、`@authority`、`@path`；存在即必签：`@query`、有消息体时的 `content-digest` 与 `content-type`、以及 `ucp-agent`、`signature-agent`、`idempotency-key`、`webhook-id`、`webhook-timestamp`）。任何遗漏当前报文中已出现必签头的签名必须被视为未覆盖关键头而跳过/拒绝。
   - **重试与乱序收敛契约**：明确 `Webhook-Id` 是**事件级标识（per-event）而非投递级标识（per-delivery）**，`Webhook-Timestamp` 是事件发生的不可变时间；商家重试失败投递时**必须（MUST）**保留原始 `Webhook-Id` 与 `Webhook-Timestamp`。由于 UCP 订单 Webhook 载荷携带订单的**完整当前状态（full current state）而非增量补丁（deltas）**，平台只需按 `Webhook-Id` 幂等去重并按 `Webhook-Timestamp` 排序应用，即可在网络乱序或重试投递下确定性收敛至最新订单状态。
2. **`d9c18e0d27c7`（2026-10-14T17:45:12Z，`#795`，`docs(checkout-rest): cover ucp-agent in the example signed request`）**：
   - 修复结账 REST 签名请求示例中存在 `UCP-Agent` 头却未列入 `Signature-Input` 覆盖集的自相矛盾问题。
3. **`5021fa83a652`（2026-10-16T07:29:41Z，`#933`，`docs: don't treat 304 Not Modified as a forbidden redirect`）**：
   - 明确 UCP Profile、JWKS 与 CIMD 端点严禁返回或跟随 `301`/`302`/`303`/`307`/`308` 重定向，但对带有条件请求头（如 `If-None-Match`）的校验请求返回 `304 Not Modified` 属于合法缓存命中而非重定向。

## 3. 架构师辩证分析：Agentic Commerce AI Native 架构 vs 云厂商 Well-Architected / 经典三层架构

结合 2026-10-16 验证的 UCP `#659`、Poppy `#36/#37/#49/#50/#51/#53` 与 Stripe MCP 迁移延期证据，经典 Web 三层架构及通用云 WAF 在落地面向交易与履约的 Agentic Commerce 时，必须在以下三个控制面完成结构性重设计：

| 架构设计维度 | 经典 Web 三层架构 / 传统云 WAF 假设 | Agentic Commerce AI Native 架构重设计（基于 2026-10-16 新证据） |
| --- | --- | --- |
| **1. 异步事件与请求签名边界：从“Body HMAC”到“闭合信封必签门禁 + 全状态时间戳收敛”** | Webhook 网关通常只校验请求体 HMAC（或 `Content-Digest`），将 `X-Request-Id`、重试时间戳视为传输层辅助日志，业务层往往依赖按序到达的增量事件（Delta Events）推进订单状态机 | **闭合“存在即必签（Closed Sign-if-Present）”门禁（UCP `#659`、`#795`）**：一旦报文出现 `Webhook-Id`、`Webhook-Timestamp`、`UCP-Agent`、`Signature-Agent`、`Idempotency-Key`，它们必须进入 RFC 9421 `Signature-Input` 覆盖集，否则即使 `Content-Digest` 正确也必须拒收；同时商家重试必须复用原 `(Webhook-Id, Webhook-Timestamp)`（若同 ID 时间戳被篡改立即拒绝），接收端以完整状态快照按 `Webhook-Id` 去重、按 `Webhook-Timestamp` 偏序收敛 |
| **2. 联合认证与会话生命周期：从“可信固定 IdP + 后台自动续期”到“防跨企断言重放 + 单账户终身锚定”** | 后端服务只对接己方固定 IdP，OAuth JWT `aud` 常设为 `token_endpoint` 或数组；连接池/后台任务在 Token 失效时自动用存储凭证静默重登 | **跨企业零信任认证（Poppy `#36`、`#37`、`#49`、`#50`、`#53`）**：个人 Agent 动态连接无数外部企业，客户端与会话断言 `aud` 必须锁定为企业 `auth.issuer` 单一字符串，阻断恶意企业篡改 `token_endpoint` 实施跨企重放；发现阶段严格比对重定向后实际提供 `poppy.json` 的主机名（不剥离 `www.`）；Session 一旦绑定账户即使登出也永久锁定该账户（换号登录返回 `400 account_mismatch`）；用户/企业吊销后严禁后台凭存储的受托凭证静默重登 |
| **3. 动作审批与多租户上下文：从“信任后端返回文案”到“不可信企业内容隔离 + Summary-vs-Terms 机器核对”** | 第一方前端无条件信任第一方后端 API 返回的确认弹窗文案（`summary`），多微服务之间默认共享用户上下文 | **双边博弈下的客户端确定性门禁（Poppy `#51` Section 8.1 & `operations`）**：企业返回的一切消息、工具结果与操作 `summary` 均属于外部不可信数据；个人 Agent 必须阻断由企业 A 内容触发的向企业 B 的跨企调用/数据外传，并在弹出用户审批前机器核对企业 `summary` 与结构化 `terms`（金额差价、商品项、支付方式）一致，防止“文案写免费换货、条款扣款 150 美元”的诱导审批攻击 |
