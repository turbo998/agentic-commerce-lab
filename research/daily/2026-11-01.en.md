## 2. Dialectical Architecture Analysis: AI-Native Commerce Workloads vs. Classic 3-Tier Web / Cloud WAF

| Dimension | Classic 3-Tier Web App / Cloud WAF | AI-Native Agentic Commerce Architecture |
|---|---|---|
| **Approval Policy vs. First-Admission Provenance** | Often stores policy status (`active`) and execution state in a single mutable order row or cache entry, making it impossible to distinguish "never attempted admission" from "admission provenance tampered". | Separates static approval policy (`payment_approvals` via `read_approval`), first-admission clock provenance (`payment_admissions` via `find_admission`), and attempt reservation/reconciliation (`payment_attempts` via `read_attempt`) across distinct tables sharing one SQLite transaction boundary without retroactive backfilling. |
| **Read-Only Inspection & Exception Disambiguation** | Commonly raises a single domain exception for both "record not found" and "validation/integrity failure", forcing callers to parse error strings. | Stage 1729 adds `PaymentApprovalStore.find_admission(operation) -> ApprovalAdmission | None`: returns `None` when unadmitted or pre-reserved without admission history, and raises `PaymentApprovalError` on 10-dimension fingerprint mismatch or corrupted timestamps. |
| **Trusted Clock Sampling Boundary** | Samples wall-clock time once at the API gateway ingress and passes it downstream. | Read-only methods (`read_approval`, `find_admission`, `read_permission`, `read_attempt`) take zero write locks and sample no clocks; only `admit()` samples the trusted clock *after* acquiring `BEGIN IMMEDIATE`. |
