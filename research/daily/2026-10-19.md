## 2. 解决方案架构师视角：AI-Native 负载架构 vs 云厂商 Well-Architected 经典三层 Web 架构六大平面系统重构

传统云厂商（AWS / Azure / GCP）提出的 **Well-Architected 三层 Web 架构（Presentation / Stateless App / ACID DB）** 建立在三大隐含假设之上：**① 人类在浏览器前实时交互（User-Present Session）**、**② 应用层代码逻辑是确定性的（Deterministic Code Path）**、**③ 交易要么同步完成要么通过幂等重试收敛，且单笔交易金额远高于支付通道固定手续费**。

在 Agentic Commerce 中，这三大假设同时失效。我们将 AI-Native 负载架构与经典三层 Web 架构的本质差异归纳为 **六大架构平面（Six Architectural Planes）**：

### 2.1 Plane 1：身份与委托平面（Identity & Delegation Plane）
- **经典三层缺陷**：Web 应用用单一 Session Cookie 或平台级 OAuth Token 代表“当前在线用户”，在多商户市场（Marketplace）中常混用平台自身的商户档案，且把存储的卡 Token 当作可重复解析的静态外键。
- **AI-Native 重构**：
  1. **通道感知令牌绑定**：OpenAPI / Operations 强制使用 RFC 9449 `DPoP` 证明持有权，MCP 通道强制使用 RFC 8707 `resource` 绑定的 `Bearer` 令牌，UCP Accelerated IdP 换票强制 `subject_token` 绑定当前单用户（`#970`）。
  2. **Connect 多商户 SPT 档案对齐**：Direct Charge 强制绑定关联商户 `network_business_profile` + `Stripe-Account` 头；Destination Charge 配合 `on_behalf_of` 时推荐绑定关联商户档案以消除账单描述符错位。
  3. **单次消费 `SPT Resolve` 与 RSA 切片提取**：外部 PSP 调用 `/v1/shared_payment/granted_tokens/{id}/resolve` 严格限单次（二次重放立即阻断），并校验 `CAVV`/`TAVV`/`DCVV` 密文与 `<field>:<start>:<length>` 无重叠切片。

### 2.2 Plane 2：状态与事务平面（State & Transaction Plane）
- **经典三层缺陷**：将支付与订单建模为单向线性 CRUD，遇到超时或风控拦截时由后台 Worker 按指数退避自动重试。
- **AI-Native 重构**：
  1. **非线性 SPT 状态回退**：支持 `active` $\leftrightarrow$ `requires_action` 双向跃迁（3DS 阶梯挑战），同时锁死 `deactivated` 终态防复活。
  2. **AP2 §7.4 受托熔断器（Fiduciary Circuit Breaker）**：区别于 Netflix Hystrix 等仅看错误率的网络熔断器，FCB 同时监控单笔限额（`VALUE_THRESHOLD`）、累计支出（`CUMULATIVE_THRESHOLD`）、窗口频次（`VELOCITY`）与商品类目越权（`AUTHORITY_SCOPE`）；一旦熔断进入 `OPEN`，**禁止时间冷却自动恢复**，必须验证人类签署的 Recovery Mandate 才能进入 `HALF_OPEN` 试探。

### 2.3 Plane 3：推理与确定性执行隔离平面（Reasoning vs. Execution Isolation Plane）
- **经典三层缺陷**：把 LLM Tool Calling 当作普通 RPC，信任外部企业返回的自然语言 `summary` 或允许浏览器自动化脚本直接点击借贷确认按钮。
- **AI-Native 重构**：在 LLM 与外部 API 之间部署确定性 **Policy Broker**——强制校验 `summary` 金额与结构化 `terms` 完全一致（阻断 Bait-and-Switch 提示词注入）、拦截跨企业内容触发的越权调用（Poppy §8.1）、对 WebMCP `consequentialHint` 强制插入人工确认门禁，并严禁脚本化自动提交 Affirm BNPL WebView。

### 2.4 Plane 4：协议互操作与批量目录平面（Protocol Interoperability & Bulk Discovery Plane）
- **经典三层缺陷**：定时任务拉取商品流时，若分片中途超时仍执行差集下架（导致在售商品大面积误删），或用增量 JSON 直接覆盖整个 `variants` 数组。
- **AI-Native 重构**：实现 UCP `dev.ucp.common.feed`（`PR #866`）与 Stripe SFTP `manifest.json` 双重屏障——逐分片校验 RFC 9530 `sha-256` 摘要，**任何分片缺失或摘要不匹配立即锁定 `deletions_permitted=False`**；对 `supplemental` 补充流按变体 `id` 原地合并。

### 2.5 Plane 5：可观测与争议取证平面（Observability & Dispute Forensics Plane）
- **经典三层缺陷**：依赖应用层文本日志应对拒付，或假定支付网关会把 Agent Mandate 自动传给发卡行。
- **AI-Native 重构**：基于 ACP ATDRP `PR #316` Section 7.4a 与 Appendix C 审计结论（17 家网关中仅 Stripe/Braintree 记录支付侧 Agent 信号，**0/17 家网关具备发卡行侧结构化 Mandate 字段**），构建确定性争议证据编译器——先 fail-closed 校验 `digest_ok`、RFC 3161 时间戳与 `payment_id` 绑定，再将 Mandate JWS 与结账哈希确定性编译至网关兜底字段（如 `uncategorized_file` / `uncategorized_text`）。

### 2.6 Plane 6：FinOps 与微支付经济学平面（FinOps & Micropayment Economics Plane）
- **经典三层缺陷**：所有扣款走同一卡通道，或在流式微支付中随意设置结算周期，导致手续费倒挂或亚美分尾差被没收。
- **AI-Native 重构**：建立 **Token 推理成本 + 支付轨损耗联合优化模型**——`> $0.50` 商品订单走 Stripe SPT 卡轨；`$0.01–$0.50` 单次机器调用走 `x402` Base `USDC`；`< $0.01` 高频流式调用走 `MPP` Tempo Sessions（最低 `0.000001 USDC`），并通过最大公约数算法将结算周期强制对齐至 `$0.01` 的最小整数倍步长（例如单价 `$0.000350` 时对齐为 `200 units = $0.07`），将亚美分尾差没收率从 **54.29%** 降至 **0.00%**。

## 3. 新增可运行技术资产与 7-Card 4:5 视觉基准报告（`2026-10-19`）

1. **六平面 AI-Native 负载架构基准与确定性护栏（[`lab/workload_arch_bench.py`](../../lab/workload_arch_bench.py)）**：
