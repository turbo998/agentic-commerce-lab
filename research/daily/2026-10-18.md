### 2.1 为什么经典 REST 的“统一 PUT 全量替换”或“统一 PATCH 合并”在 Agent 负载下都会失效？

- **正题（经典 Web 三层 CRUD 假设）**：传统 Web 结账页面由浏览器 DOM 维护完整表单状态，每次提交 `PUT /checkout` 全量替换资源简单清晰；或者使用 JSON Merge Patch 只传改动字段。
- **反题（Agent 增量推理与法务合规冲突）**：Personal Agent 在多轮交互中常针对局部子任务调用工具（例如第 1 轮确认商品与营销同意，第 2 轮仅修改收货地址）。若机械套用 `PUT` 全量替换，第 2 轮未重传 `buyer.consent` 就会将用户刚确认的隐私/营销授权静默重置为商户默认值；反之，若允许对 `consent` 做残缺字段的宽松局部 PATCH，平台又可能漏读商户新增的合规宣告项，或把用户在商户 A 的“允许短信营销”擅自以 `source: "platform"` 复制到商户 B。
- **合题（AI-Native 混合状态契约）**：
  1. **资源级全量替换 + 合规子域显式豁免（UCP `#660`）**：对 `line_items` 等商业意图字段保持全量替换（消除多轮残留商品），但对 `buyer.consent` 实施豁免——省略 `consent` 字段时保留既有状态。
  2. **一旦提交即要求完整宣告回传与作者归属校验**：当请求包含 `consent` 时，必须回传商户宣告的每一个 purpose 与 segment，未获用户针对该商户显式表态的项必须原样回传商户默认值与 `source: "business"`；且在 `complete_checkout` 阶段把同意项的数据依赖（如短信同意依赖 `phone_number`）升级为硬性完成门禁。

### 2.2 为什么必须剥夺 Agent / 平台的“日期与政策推算权（No Platform Date Math）”？

- **正题（传统 BFF/前端便利计算）**：在传统电商应用中，BFF 或前端看到 `"duration": "P30D", "anchor": "delivered"`，往往直接在客户端用 `delivered_at + 30 days` 算出退货截止日展示给用户。
- **反题（LLM 与跨平台解释漂移）**：LLM 极易把“未结构化声明退货期限（省略 `eligibility`）”幻觉为“无限期退货（`unlimited`）”，或在跨时区、商户营业日历、节假日顺延场景下自行计算 `anchor + duration` 给出错误的承诺日期，进而引发消费争议；同时又容易把“`window` 已过”当成硬性拦截条件拒绝协助用户联系售后。
- **合题（商户权威时间戳与下限语义，UCP `#966`）**：AI-Native 协议将政策“条款（`duration` + `anchor`）”与“已解析实例（`expires_at`）”显式分离——只有商户服务端有权产出 `expires_at`；平台与 Agent 严禁做日期加法，严禁对省略字段做正/负向推断，且将窗口期视为商户承诺的“最低保障下限（Floor）”而非“禁止提交上限（Ceiling）”。

### 2.3 为什么下游超时在 AI-Native 控制面中严禁映射为 `failed`？

- **正题（云原生 WAF 常规超时处理）**：经典微服务在同步网关超时后常返回 `504` 或标记任务失败，交由调用方重试。
- **反题（Agent 自主换路重试放大副作用）**：与只会按固定 `Idempotency-Key` 原路重试的确定性客户端不同，LLM Agent 一旦收到操作 `state: "failed"`，往往会自主改变策略（例如换一个 SKU、换一张卡或通过另一通道重新发起新提案），如果原下游实际已扣款或已改单，就会造成双重副作用。
- **合题（Poppy `operations` §§4, 6, 7 的不确定态驻留与跨通道收敛）**：当确认执行遇到下游超时、真实结果未知时，企业状态机**必须停留在 `in_progress`** 并附带 `Retry-After`，把“结果未知”显式暴露给 Agent；即使此时收到 `POST /cancel`，只要企业尚未确认下游已停止，也必须继续返回 `in_progress` 而非虚假的 `cancelled`；同时在提案阶段对跨通道（Conversation 与 OpenAPI）相同 `terms` 自动去重。

## 3. 应用场景深化：跨通道改单超时恢复与合规同意/退货门禁

1. **场景 A：用户在对话与 OpenAPI 双通道发起同一改单 + 下游仓配超时 + 跨设备查询（Poppy `operations` v1）**
   - **流程**：Personal Agent 先在对话后通过 OpenAPI 提出修改待发货订单商品，企业校验客户端声明了 `"operations"` 扩展后返回 `202` 提案；若同一账户另一 Session 再次发起相同 `terms` 提案，企业直接返回既有 `proposed` 操作（防重复建单）。用户确认后，若企业仓配系统响应超时，操作保持 `in_progress` 并返回 `Retry-After: 7`；此时若用户尝试取消但仓配尚未确认停止，操作仍保持 `in_progress`，直至仓配回执确认完成后跃迁至 `succeeded` 并写入非空 `result.summary`。
   - **未登录访客隔离**：对于未登录访客发起的操作（如匿名报价锁定），仅创建它的 `session_id` 可查询或取消，同一用户的其他未登录 Session 访问一律返回 `404 operation_not_found`。
2. **场景 B：多轮结账中的营销同意保留、短信依赖阻断与退货政策零算日展示（UCP `buyer_consent` + `policy.return`）**
   - **流程**：商户宣告 `analytics`（默认 `true`）与 `marketing`（默认 `false`，含 `email`/`sms` 子段）。买家授权开启 `sms` 营销但尚未填写手机号：`create_checkout` 允许创建并返回 `missing_consent_data` 警告；后续修改收货地址时请求省略 `buyer.consent`，系统保留既有同意配置；若直接调用 `complete_checkout` 而仍无 `phone_number` 则确定性阻断完成。展示退货政策时，仅使用商户返回的 `expires_at` 权威时间戳，拒绝对仅有 `P30D` 条款的策略做本地日期推算。
