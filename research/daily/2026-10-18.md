### 2.1 为什么经典 RPA/爬虫式浏览器自动化与静态 MCP 工具表在结账界面会失效？（Stripe WebMCP & Embedded Affirm 规则）

- **正题（传统浏览器自动化与静态 Tool Calling）**：在传统测试或早期 Browser Agent 中，开发者要么用脆弱的 DOM 选择器模拟点击，要么在会话启动时一次性读取工具 JSON Schema 并直接调用提交。
- **反题（支付方式切换引发的 Schema 漂移与金融借贷合规红线）**：
  1. 在 Stripe Checkout / Payment Element 中，用户从卡支付切换到银行转账或本地钱包时，表单必填项会实时变化；若 Agent 缓存初始工具 Schema，会提交残缺字段或误触错误控件。
  2. 更危险的是，开发者容易把 WebMCP 工具元数据中的 `consequentialHint` 误解为“已带安全标记可自动执行”，或者让 Agent 在 WebView 内自动帮用户点击 Affirm 分期贷款协议。
- **合题（WebMCP 动态重发现 + `consequentialHint` 硬门禁 + BNPL 人类导航主权）**：
  - **状态变更触发重发现**：任何改变支付方式或表单状态的动作后，Agent 运行时必须使旧工具缓存失效并重新发现当前可用工具与 Schema。
  - **`consequentialHint` 触发本地确定性确认门禁**：宿主运行时拦截所有带 `consequentialHint` 的工具调用，在向用户展示最终金额与收款方并获得显式确认前拒绝放行。
  - **BNPL 人类导航禁区**：对 Affirm 等消费信贷流程，架构上严禁无头浏览器或 Agent 脚本注入点击，必须在具备完整导航控制权的用户设备上由买本人完成确认。

### 2.2 为什么经典“宽进严出（Postel's Law）”在跨组织商业协议中是反模式？（UCP `#940`、Stripe OCA 与 SFTP `manifest.json`）

- **正题（传统 Web 服务的宽松兼容）**：经典 Web API 常遵循“忽略未知/不支持的参数并尽量用其余参数完成请求”，例如同时收到 `cart_id` 和 `line_items` 时若不支持购物车就只按 `line_items` 结账。
- **反题（商业意图静默分叉导致错买/漏买）**：在 UCP PR `#940` 中，如果平台以为商户支持 `dev.ucp.shopping.cart` 而传入 `cart_id`（并在 `line_items` 中仅放了占位或旧快照），商户若静默忽略 `cart_id` 回退到 `line_items`，就会按错误的商品清单扣款！同理，在百万级商品 SFTP 同步中，若摄取器不等 `manifest.json` 到达就提前消费已上传的部分分片并执行主目录隐式删除，会导致未上传分片中的在售商品被大面积误删。
- **合题（显式拒绝未协商参数 + 批次完成屏障 + 非对称终止锁）**：
  1. **UCP `#940` 严格互斥与拒绝回退**：未协商 Cart 能力时收到 `cart_id` 必须显式报错拒绝，绝不静默回退到 `line_items`；已协商且同时传入时，以服务端权威 Cart 内容为准。
  2. **SFTP `manifest.json` 原子屏障与 `disable_checkout` 隔离**：仅当 `manifest.json` 最后到达且校验全部 `total_shards` 齐备后才触发目录切换；对 `disable_checkout=true` 的发现型商品在编排层硬性阻断 `RequestedSession` 创建并降级为外部链接跳转。
  3. **Stripe OCA 非对称重发起锁**：仅卖家可发起初始协议；一旦协议被某一方终止（如 Agent 因风控终止卖家，或卖家因渠道策略终止 Agent），**只有发起终止的一方才能重新发起新协议**，防止被封禁方通过自动化脚本无限重发握手请求骚扰对方。

### 2.3 为什么混合状态合并、零平台算日、下游超时驻留与争议证据包准入必须内置于控制面？

- **混合状态合并（UCP `#660`）**：商品行采用全量替换防残留，但 `buyer.consent` 豁免全量清空；提交 `consent` 时必须完整回传已宣告键，仅买家对该商户显式表态才可标 `source: "platform"`，且将短信同意所需的 `phone_number` 在 `complete` 阶段升格为阻断门禁。
- **剥夺平台日期计算权（UCP `#966`）与下游超时驻留（Poppy `operations` §6）**：平台严禁用 `anchor + duration` 自算退货截止日 `expires_at`；确认操作遇下游超时必须驻留 `in_progress` + `Retry-After`，严禁误报 `failed` 诱导 Agent 换路重下新单。
- **单用户换票绑定（UCP `#970`）与 ATDRP 证据包 Fail-Closed 准入（ACP `#316` §7.4a）**：RFC 8693 换票严禁跨用户复用或用服务账号令牌代换；争议裁决前先验算证据包摘要与 RFC 3161 时间戳，将未固定公钥的生产者日志降级为仅作一致性参考，并确立**“买家沉默（`no_record`）绝不等于数字商品验收通过”**的铁律。

## 3. 应用场景深化：嵌入式跨商户结账、服务预订、浏览器 WebMCP 与争议裁决

1. **场景 A：AI 购物助手嵌入式结账与 SFTP 百万商品目录同步（Stripe Embedded Commerce + SFTP Feed + OCA）**
   - **流程**：卖家发起 OCA（`/v2/orchestrated_commerce/agreements`），Agent 验证卖家身份后调用 `/confirm` 完成双向签约；Agent 通过 SFTP 每 24 小时摄取卖家 `Product Master Feed`、每小时摄取 `Delta Feed`，以 `manifest.json` 为完成屏障，对 `disable_checkout=true` 的商品仅展示跳转链接，对可结账商品调用 `POST /v1/delegated_checkout/requested_sessions`（`2026-04-22.preview`）并在确认时附带 `RadarSession` 与设备信号签发单次 SPT；若卖家实时库存接口异常则返回 `424 Failed Dependency` 并中止扣款。
2. **场景 B：餐饮/酒店/本地服务 Agent 预订与长周期 SPT 担保（Stripe Service Bookings + UCP Payment Handler）**
   - **流程**：Agent 通过 `search_availability` 查询时段，调用 `create_booking` 锁定 `booking_id`（状态 `awaiting_payment`，若时段已被抢占则捕获 `409 slot_unavailable` 重新检索时段）；随后向买家展示含取消条款的最终价格，获取最长 180 天有效期的 SPT 并携带至少保留 24 小时的 `Idempotency-Key` 调用 `complete_booking`。
3. **场景 C：浏览器内 WebMCP 辅助结账与跨通道售后改单/争议取证（Stripe WebMCP + Poppy `operations` v1 + ACP ATDRP §7.4a）**
   - **流程**：对于尚未接入 API 的长尾商户，Browser Agent 通过 Chrome WebMCP 在 Stripe Checkout 页面动态发现表单工具，切换支付方式后强制重发现 Schema，并在调用带 `consequentialHint` 的支付提交工具前暂停等待用户确认（遇到 Affirm 贷款页面则完全交由用户手动操作）。售后阶段通过 Poppy `operations` v1 跨通道去重改单；若发生数字服务交付争议，按 ACP ATDRP Section 7.4a 校验独立 `checker_key` 与事前验收标准，拒绝商户以“买家超时未回复”主张自动验收。
